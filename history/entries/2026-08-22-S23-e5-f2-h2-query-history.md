## Objective

Give `history` its read side — `listRuns`/`getRun` use cases over the `RunStore` port `[E5.F2.H1]` left write-only — so a repo's persisted run history (`runs/<repo>/<ts>/`) can actually be listed and retrieved, with corrupt/partial runs surfaced rather than breaking the listing (issue #34's two acceptance criteria).

## Deviations

- **ST-1 forced an out-of-plan file edit.** Adding `list`/`get` to the `RunStore` *interface* broke `tsc` against `run-store-fs.ts`, the interface's only existing implementor — no way to keep `npm run check` green at the stage boundary without touching it. Added throwing stubs a stage earlier than `plan.md` assigned; flagged explicitly in `execution-log.md`. ST-3's scope was unchanged (it replaced the stubs rather than adding new methods).
- **ST-3's mutation testing surfaced a real test-coverage gap, not a code defect.** Removing `list()`'s explicit `.sort()` call didn't fail the "ascending order" contract test — this environment's filesystem happened to already return `readdir` entries pre-sorted, so the portable contract suite could not actually prove AC-2's readdir-order-independence claim. Recognized and recorded rather than silently discovered later; the real proof (a mocked reversed `readdir`) was confirmed still-planned for ST-4, which then delivered it.
- **Full-4r code review found 2 confirmed CRITICAL defects**, both introduced by this story and both deterministic (no refuter pass needed — 0 inferential-severe candidates qualified): `get()` misclassified a corrupted-but-present run as not-found instead of corrupt (contradicting `list()`'s own classification of the identical state); `list()` aborted its entire result on a single entry's raw fs error instead of degrading just that entry. Both independently re-verified by Claude via direct code reading before merging into the ledger, not merely trusted from the lens reports. Fixed in an added ST-5, each fix independently proven by mutation (revert → dedicated regression test fails for the exact claimed reason → re-apply → clean).
- **`state.yaml` schema violations, caught only once real `jsonschema` validation was actually run** (Python's `jsonschema` library against `sdd-lite/schemas/state.schema.yaml`, not the `yaml.safe_load`-only check used earlier in the session and inherited from `[E5.F2.H1]`'s pattern): invalid `next_action.kind` values (`user_checkpoint`, `proceed` — not in the schema's enum), a missing required `sddl-qa-review` stage stub, a missing required `qa_report` artifact path, and an out-of-enum `complexity_assessment.confidence` value (`medium-high` — only `low`/`medium`/`high` are valid). All fixed in this change's `state.yaml`. **Process note**: the identical `confidence` violation exists in the already-merged, closed `[E5.F2.H1]` sibling `state.yaml` — verified but not touched (that change is closed) — a real gap in prior sessions' informal validation worth carrying forward as a lesson for future `state.yaml` work.
