## AC-16/AC-17 Test Strategy (the gap design.md flagged for plan to close)

Design.md's Open Technical Questions table is explicit that a fixture-replaying `runProcess` stub **cannot** prove SIGTERM-then-SIGKILL ordering: the seam type carries no scheduling, and a stub bypasses `execa` entirely, so nothing inside a stubbed test ever spawns a process or waits on a real signal. Two different, complementary tests are required in ST-4 — neither is "add a test," both are named exactly:

1. **The option-wiring test (the actual proof of AC-16/AC-17).** `vi.mock("execa")` at the top of the test file, capturing the mocked `execa` export. Import `process-runner.ts`'s exported factory (ST-2's `createDefaultRunProcess(binaryPath)` or equivalent) directly — not through the adapter — call the returned `ClaudeCodeProcessRunner` once with `{ cwd, input, timeoutMs: 5000 }`, and assert the mocked `execa` was called with `expect.objectContaining({ timeout: 5000, killSignal: "SIGTERM", forceKillAfterDelay: 2000, reject: false })`. A second `it` calls it with `timeoutMs: 0` and asserts the call options do **not** contain `timeout`/`killSignal`/`forceKillAfterDelay` keys at all (proving the conditional spread, `exactOptionalPropertyTypes` compliance). This is what design.md means by "a stub-level unit test for AC-16/17 asserts the adapter passes the right execa options" — it is the ceiling of what CI can prove.
2. **The adapter-reaction tests (already implied by AC-13/AC-14/AC-18, restated here so they are not skipped as "duplicate" of #1).** Two `it`s using a scripted `runProcess` stub on the real-invocation call: one resolving `{ stdout: fixture("timeout-sigterm.json"), exitCode: 1, signal: "SIGTERM", timedOut: true }` → asserts `review()` rejects `ClaudeCodeReviewError` (the SIGTERM-flushed-JSON path); one resolving `{ stdout: "", exitCode: undefined, signal: "SIGKILL", timedOut: true }` → asserts `review()` rejects `ClaudeCodeInvocationError` (the SIGKILL-empty-stdout path). These prove the adapter classifies both post-signal outcomes correctly — not that `execa` escalated correctly between them.

What neither test proves — and what nothing in CI can prove — is that a real child process actually receives SIGTERM first, is given a real grace window, and only then receives SIGKILL. That is exactly what ST-5's manual AC-24 run is the closest available evidence for, though even that run only proves the mechanism *if* the manually-invoked review happens to exceed `timeoutMs` (a successful review, which is what AC-24 literally asks for, will not exercise the kill path at all). This is a known, accepted residual gap — the same one design.md's Open Technical Questions table already recorded (AC-19's residual risk) — not a defect in this plan; do not attempt to fabricate an automated real-process test to close it (that would require spawning `sleep`-like behavior from the real `claude` binary, which is out of this story's scope).

- `describe("error translation (AC-23)")` — one `it` per error path asserting `rejects.toBeInstanceOf(Error)` beyond what the shared contract already covers is not needed (contract suite already does this); a doc-comment/mechanical check instead that no path in `review()` throws synchronously (inspection, not a runtime test, matching AC-23's own validation hint).

## Validation Strategy

- **Per stage.** ST-1/ST-2/ST-3 are leaf-file stages, matching H1's ST-1/ST-2 pattern (cited by H2's plan.md as precedent): nothing in the existing tree imports the new files until ST-3 completes and ST-4 tests them, so their exit condition is `npm run check` green plus `npm test` staying at the measured baseline (226/226) — a real signal (a broken import or a type error would fail `check`), just not yet a signal about the new logic's correctness.
- **ST-4 is the only stage with new automated coverage** and is where AC-3 through AC-23 (except the process/manual ones) actually become provable. Fast loop first (`npx vitest run --project adapters -t "claude-code"`), full gate only once green.
- **ST-5 is the only stage with a non-automatable exit condition.** Its manual run must be recorded with the literal command, exit code, and `VERDICT:` line in `execution-log.md` — not summarized as "ran successfully." The throwaway script used for the run is not committed to the repo (same convention H1's ST-1 evidence run used for its own throwaway script).
- **Cross-boundary note.** `.dependency-cruiser.cjs` excludes `__test__/` paths from `depcruise src`, so `claude-code-adapter.test.ts`'s `vitest`/`vi.mock("execa")` usage is sanctioned test-only scaffolding — the `core-no-io-libs` guard applies to `src/core/**` production code only, and this whole story touches no core file.

## Dependencies And Sequencing

- ST-1 → ST-2: sequencing choice, not a true import dependency — `process-runner.ts` imports nothing from `errors.ts`/`envelope.ts`. Sequenced this way anyway because ST-1's files are the ones design.md calls "pure, no execa dependency, easiest to land and unit-test first," so if either needs revision after a `check` failure, it is cheap to redo before the execa seam is built on top of it.
- ST-2 → ST-3: true dependency. `claude-code-adapter.ts`'s factory calls the ST-2 factory as its default `runProcess` when the caller doesn't supply one.
- ST-1 → ST-3: true dependency. `review()`'s steps 3–5 call `parseEnvelope`/`extractSuccess`/`buildReviewErrorMessage` from ST-1.
- ST-3 → ST-4: true dependency. The test file imports `createClaudeCodeAdapter` from the finished adapter (and, for the AC-16/17 test, `process-runner.ts`'s factory directly).
- ST-4 → ST-5: true dependency. ST-5's manual run exercises the same adapter ST-4 just proved passes its automated suite — running the manual verification against an untested adapter would waste the one non-repeatable, real-API-cost data point AC-24 asks for.
