## Contract Fix Soundness — Independent Re-Derivation

Re-derived the `ReviewEngine.contract.ts` fix from first principles rather than trusting execution-log.md's self-report:

- **Original problem, confirmed real.** The original "propagates the configured usage" test configured `harness.resolving("OUT", { totalTokens: 42 })` — a `ReviewUsage` with only `totalTokens` set, no `inputTokens`/`outputTokens`. `envelope.ts`'s `extractSuccess` (the only place `claude-code`'s `ReviewUsage` is ever constructed) can *only* produce a `usage` object with all three fields set together (`inputTokens`, `outputTokens`, and their sum as `totalTokens`) or no `usage` at all — there is no code path that produces a lone `totalTokens`. So the original test was genuinely unsatisfiable by any derivation-based real engine, confirming this was not a fabricated blocker.
- **The fix.** Changed the configured usage to a full tuple: `{ inputTokens: 10, outputTokens: 32, totalTokens: 42 }`. Verified `10 + 32 === 42` — the tuple is internally consistent with `extractSuccess`'s own summation rule, which is what makes it satisfiable by a derivation-based engine at all (a mismatched tuple, e.g. `{inputTokens: 10, outputTokens: 32, totalTokens: 99}`, would have been unsatisfiable by construction and the fix would have been unsound).
- **`claude-code`'s harness re-derived independently.** The test file's `resolving` factory (lines 88-107) builds `{ is_error: false, result: output, usage: { input_tokens: usage.inputTokens, output_tokens: usage.outputTokens } }` only when both `inputTokens`/`outputTokens` are defined — passing the shared contract's configured `{10, 32, 42}` through, `extractSuccess` recomputes `totalTokens = 10 + 32 = 42`, matching the configured value exactly. Confirmed by reading the harness code directly, not assuming it works.
- **`FakeEngine`'s harness unaffected.** `fake-engine.ts` (read directly) is a pure literal passthrough — `outcome.result` is returned exactly as configured, with no derivation logic at all. The new full-tuple `usage` object passes through it unchanged regardless of whether the numbers are internally consistent. Confirmed the fix does not regress `FakeEngine`'s own contract-suite run (part of the 250/250 total this review re-ran).
- **Genuine property preserved.** Both before and after the fix, the test's actual assertion is `expect(result.usage).toEqual(usage)` — "whatever usage the harness is configured with comes back out unchanged." The fix only changes *which* `usage` object is used as the fixture, not what property is being tested. Confirmed sound: the fix is a legitimate repair of a badly-chosen fixture, not a weakening of the test's intent.

## Notes (non-blocking, do not affect the `pass_with_notes` verdict)

1. **AC-9's "missing/non-string `.result` despite `is_error:false`" branch has no dedicated test.** `extractSuccess`'s guard (`envelope.ts:35-39`) is present and correct by direct reading, but no test in `claude-code-adapter.test.ts` exercises `{is_error:false}` with a missing or non-string `.result` field to confirm it actually throws `ClaudeCodeInvocationError` at runtime rather than, say, passing `undefined` through as `output`. This is a narrow, easily-added test-coverage gap, not a code defect (the guard clause is unambiguous when read).
2. **AC-15's suggested "never-resolving pre-check stub" test is absent.** `review()` has no adapter-level timeout wrapper around the pre-flight `await runProcess(...)` call — it delegates entirely to whatever `runProcess` implementation is supplied, trusting it to honor the passed `timeoutMs`. This is consistent, documented design intent (design.md: "passed through the *same* `runProcess` seam... proving the seam is genuinely uniform"), and the default `execa`-backed runner's timeout-passthrough is proven by the AC-16/17 mock test using the same options shape. But a custom `runProcess` that ignores `timeoutMs` would genuinely hang `review()` indefinitely — nothing in `review()` itself bounds it. Spec's own suggested validation approach (a hanging stub) is not present in the suite. Not a functional regression against any documented behavior, but a real gap between the AC's suggested test and what ST-4 delivered.

Neither note involves invoking a real `claude` CLI or touching any file — both are read-only observations for the record.
