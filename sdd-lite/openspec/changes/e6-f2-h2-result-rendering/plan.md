### The design question `e6f2h2-D16` raised, resolved

The handoff named the hazard precisely: the digest renders `finding.text` (the matcher's **remainder group**) while the full view renders the **neutralised line**, so any fix that normalises one input for matching and a different one for rendering can desynchronise the two surfaces. Four mechanisms were considered and probed:

| # | Mechanism | Digest | Full view | Verdict |
|---|---|---|---|---|
| C-A | Trim the **raw** line before neutralising, for the match path only (two derived strings per line) | leading controls disappear before the marker: the match is restored **for the leading position only** | renders the untrimmed neutralised line; the colour predicate is computed from the *other* variant, so a finding can be listed in the digest and left uncoloured in the full view unless the predicate is recomputed | **rejected** — desynchronises the surfaces unless a second pipeline is threaded through both, puts a raw `trim()` upstream of neutralisation (AC-18 says "before any other processing"), and is **incomplete**: it cannot reach a control that sits *after* a list marker (`- ␋[SEV: …]`) or *inside* the marker (`[SEV:␋blocker]`), both of which round 1 also broke |

That is R1-001's channel class, re-opened to fix a parsing bug |
| C-C | Drop leading members of N inside `splitEngineLines` / `toSafeLines`, as the CRLF terminator already is | correct | the hostile byte is **deleted** instead of shown | **rejected** — contradicts the module's explicit "nothing is removed" stance and AC-18's "no other transformation"; would need a spec amendment, which this round has no budget for |
| **C-D** | **Chosen. ### The mechanism, precisely (executor contract)

In `tui/findings.ts` only, keeping the module at **zero imports**:

1. One named source string for the space class — real whitespace plus the five tokens — used to compose the three regexes, so the class is defined **once**. `new RegExp` composition is deliberate: spelling the class inline would copy a 40-character alternation five times into one regex literal (the readability defect R2 already flagged elsewhere in this change) and invites copy-paste divergence. It is the file's first `new RegExp`; `biome check` on the patched file is clean.
2. `LEADING_SPACE` — `^<class>+`, applied after the existing `line.trim()` and before the list/quote strip. `trim()` stays: it still removes real whitespace, and the two compose (` ␋ [SEV: …]` works).
3. `LIST_OR_QUOTE_PREFIX` — its `\s+` becomes `<class>+`.
4. `FINDING_LINE` — its three `\s*` become `<class>*`. The remainder group stays `([^\n]*)` (AC-19 layer 2, untouched) and the trailing `.trim()` on the remainder stays as it is, so a token **inside or at the end of** the finding text is still rendered, never deleted.
5. The module doc-comment gains the invariant in one sentence — *an AC-18 token standing for a code point that JS whitespace absorbed is treated as that whitespace, at every structural position, and nowhere else* — plus the pointer to `engine-text.ts` that names the coupling to the token shape.

**Deliberate non-parity, to be asserted rather than discovered**: a token that trails the finding text (`[SEV: nit] x␋`) is **kept** in `finding.text` where the pre-round matcher trimmed the raw byte away. Keeping it is the safe direction — evidence preserved, nothing deleted — and it is the only text divergence C-D introduces beyond the intended "control is now shown as a token".

**Whitespace-sensitivity audit (do this and record it, it is what proves the class is closed)**: every step that consumes *already neutralised* text was enumerated. `findings.ts`' matcher is the only whitespace-sensitive one. `collapseToOneLine` and `formatTuiErrorLine` run on the **raw** message *before* `neutralizeControls` (`render.ts:285-287`), and `tui-flow.ts:317`'s blank guard runs on raw `engineOutput`.
