## Dependencies And Sequencing

- Hard chain: **S1 → {S2, S3} → S4 → S5 → S6 → S7**. S2 and S3 are mutually independent (disjoint files, neither imported by anything yet). S4 needs both (`findings.ts` for extraction, `colors.ts` for `TuiPalette`/`PLAIN_PALETTE`).
- **S1 first and S7 last are binding** (D6): S1 because `[E6.F2.H1]` proved that a guessed dependency version stops the executor mid-stage; S7 because AC-17's closeout must describe what actually landed.
- **Why the S4/S5 split, and why `formatTuiResult` survives one stage**: `tsc --noEmit` typechecks the test files, and `result.test.ts` imports `formatTuiResult` while its flow assertions pin the flow's literal output. Removing the function, switching the call sites and rewriting the assertions is therefore one atomic *green* unit. Splitting it as "S4 adds, S5 supersedes" is what makes D6's requirement real: S5's diff is a deletion-and-replacement of exactly the `[E6.F2.H1]` assertions, with a 20-line flow edit beside it, instead of the supersession being buried inside a large feature stage.
- **Recommended batching**: **S2 + S3 under one `stage_approval`** — disjoint new files, no existing behaviour touched, both validated by the same narrowed adapters run, ~60 lines together. Everything else stays one stage per `sddl-executor` invocation: S4, S5, S6 each change an existing surface, and S7 is the closeout.
- Execution stays strictly sequential regardless of batching — one approved stage (or approved batch) per invocation.
