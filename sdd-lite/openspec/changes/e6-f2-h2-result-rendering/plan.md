### Dependencies And Sequencing (fix round 1)

- Hard chain: **S7 -> S8 -> S9 -> S10**, strictly sequential, no batching. S8 is a new module nothing imports, so it lands and is covered before anything is rewired — the same shape that made S2/S3 safe. S9 cannot start before it (`render.ts` imports it). S10 cannot start before S9, because AC-20's mutation checks must run against the final rewired code, not against a moving target.
- **Why three stages and not one**: S9 is the only stage with production blast radius, and folding S10's test-verification repairs into it would mix a behaviour change with the repairs meant to prove behaviour is verified — the reviewer would lose the clean diff. Folding S8 into S9 would put the primitive and its first callers in one diff, which is exactly what the S2-S4 sequencing avoided.
- **Why S9 is one stage and not two**: `tsc --noEmit` typechecks the test files, and `extractFindings`' signature change breaks `render.ts`, `findings.test.ts` and (through the digest) `result.test.ts` simultaneously. Splitting it leaves an intermediate red stage, which the S4/S5 precedent exists to prevent.
- The ordering **split, neutralise, match, colour** is load-bearing and no stage may reorder it: the palette's SGR is added *after* neutralisation so it is never itself escaped. Any future stage that rewires must preserve it.
