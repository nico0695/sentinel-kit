## Delegation Heuristics

- Keep the orchestrator thin.
- Inline only local routing decisions that require at most 3 repo files.
- Delegate when routing, planning, or execution needs 4 or more repo files.
- Delegate read-plus-write work together when implementation is likely.
- Delegate `sddl-proposal`, `sddl-spec`, `sddl-design`, `sddl-plan`, `sddl-executor`, and `sddl-qa-review` as fresh workers by default.
- Do not run builds, installs, or broad tests inline in the orchestrator.
- Prefer artifact paths and short digests over copied artifact bodies.

### repo_conventions

- Persisted artifacts stay in English even when chat is Spanish.
- Runtime files stay under `./sdd-lite/`.
- `state.yaml` is the resume anchor; stage artifacts keep semantic detail.
- Do not invent runtime paths outside `./sdd-lite/`.
- Source of truth is `docs/prd-sentinel.md` (product, architecture), `docs/setup-tecnico-sentinel.md` (stack),
  `docs/backlog-mvp-sentinel.md` (scope). PRD §4 rules are mandatory, not advisory.
- Conventional commits. One PR per backlog story, titled `[E<epic>.F<feature>.H<story>] Title`.
- Never merge PRs, never push to `main`. Max 5 open PRs at once.
- ⚪ optional stories are out of scope unless explicitly requested.

### architecture

- Hexagonal, dependencies inward. `src/core/**` must not import from `src/adapters/**`, `src/main/**`, or any I/O
  library — whitelist is `zod` only.
- Core modules import each other exclusively via the other module's public `index`.
- Adapters never import other adapters; they share only core port types.
- Adapters are instantiated in `src/main/` and nowhere else.
- Use cases are the only core API — no domain logic in CLI or TUI commands.
- Ports are named for the domain role (`ReviewEngine`, `RunStore`), never for the implementation.
- No `services/` or `utils/` folders inside core.
- Adapters translate raw exceptions into port errors; every run ends in a terminal state:
  `ok | ambiguous | engine-error | timeout | validation-failed`.

### execution

- `sddl-executor` runs one approved stage per invocation.
- Stop on contradiction, scope drift, or blast-radius expansion.
- Do not perform hidden git side effects.
- Record changed files, checks run, blockers, and next action in `execution-log.md`.
- If a story conflicts with the PRD, or reality contradicts a documented assumption: stop and ask. Do not
  improvise scope.
- E0 through E5 have landed on `main`. All four scripts (`check`, `test`, `build`, `dev`) are runnable and
  green — verified 2026-08-23 against `main` @ `1e7cf01` (`check` clean, `npm test` 500/500 across 28 files).
- `src/adapters/driving/{cli,tui}` are still empty placeholders and `src/main/cli.ts` is still the `--version`
  stub from `[E0.F1.H3]`. E6 is the epic that fills them; `main/cli.ts` is the composition root and hot-path.

### testing

- Prefer the smallest meaningful validation set for the approved stage.
- Final review should start from configured quality commands, then narrow or expand as evidence requires.
- If a useful automated check cannot run, say so explicitly and record the gap.
- Quality gate is `npm run check` plus `npm test`. Both must pass before opening a PR. Both are runnable and
  green today (`check` = `biome check . && tsc --noEmit && depcruise src`; `npm test` = vitest, 500 tests).
- Test placement: core = unit with in-memory port fakes; driven adapters = shared contract suite per port;
  e2e = smoke of the full flow with FakeEngine. Test files live in `<module>/__test__/*.test.ts`.
- Vitest projects: `core` (`src/core/**/__test__/**`), `adapters` (`src/adapters/**/__test__/**`), `e2e`
  (`e2e/**` — still empty; the smoke suite is `[E7.F1.H1]`). Single project: `npx vitest run --project core`; single test: `npx vitest run -t "<name>"`.
- Real engine output fixtures live in `fixtures/{claude-code,opencode}/` (E1.F1.H3) and are the input for the
  E4 adapter contract suites — never invent engine output shapes.

### review

- Findings should be concrete and evidence-backed.
- `stage` review never closes the change.
- Only `final` review with a clean `pass` may mark the change completed.
- 4R triage: trivial diffs get no lens, standard diffs exactly one, hot-path or >400 changed lines get all four plus one refuter pass.
- Severity floor: only BLOCKER/CRITICAL findings enter the fix loop; WARNING/SUGGESTION are recorded once as `info` and never block.
- Precision gate: report only real, user-impacting defects with concrete evidence; when in doubt, stay silent.
- Budgets are hard caps: one sweep per lens (two in full-4r), max two fix rounds per review lineage.
- Review workers are read-only; only the orchestrator writes `review-ledger.md`. Fixes always flow through `plan.md` and `stage_approval`.
- `sddl-judgment-day` is opt-in, replaces 4R for its target, and confirms only what both blind judges agree on.
- An architecture-guard violation is a BLOCKER, never a suggestion.

### risk_zones

- Multi-area changes may require `macro-plan-first` or escalation.
- Dirty local changes are acceptable only when they do not materially conflict with the approved stage.
- Persisted evidence beats chat memory when they conflict.
- Engine adapters (`engines/claude-code`, `engines/opencode`) are now **spike-resolved**: canonical invocation,
  permission posture, timeout/kill behavior and failure signatures are documented in `docs/engines/claude-code.md`
  and `docs/engines/opencode.md`. Treat those docs as authoritative and do not re-derive invocation details.
  Flags were verified only against Claude Code `2.1.226` / OpenCode `1.17.9`.
- Anything touching the `core/` boundary or `main/` wiring is hot-path: it is the guarantee the whole design rests on.
